# 工作原理

LEGOGOD 的核心不是“让模型直接画出积木”，而是**模型只产出结构化设计，程序固定主链负责校验、求解与产物生成**。这样每一步都有可复现的检查点，生成结果才可能真的拼得起来。

## 从需求到作品的链路

```text
一句需求
  → 模型规划：目标规模、部位清单（立体部位 / 表面涂装）
  → 模型设计：三维体元与操作（或二维分层画稿）
  → 程序编译体素 + 部位绑定 + 部位突显门禁（不合格则程序反馈、模型局部修订）
  → 设计预检（支撑 / 连通 / 规模）
  → 铺砖求解：按库存与凸点连接关系精确覆盖，必要时局部图修复
  → 统一校验：覆盖、库存、凸点连接、零件级连通、装配重放、悬吊物理、稳定性
  → 生成拼装步骤 Markdown + 3D 视图
```

关键点：

- **模型输出受限协议**：模型只写规定的 JSON（算子或字符画稿），不直接决定最终每一块砖；程序在模型输出越界、缺部位、吞没必需部位时直接报错并反馈。
- **部位门禁**：立体部位必须真的“凸出来”（悬伸、轮廓阶跃、薄壁/斜面等可验证判据），表面涂装必须全部外露且与邻格异色；贴花式伪部位会被拦截。
- **精确铺砖**：求解器逐层自下而上，保证每块砖都有真实凸点承托，跨层错缝，库存不足时按同色系回退并记录。
- **统一校验**：每个交付方案都要通过覆盖、库存、凸点连接、零件级连通、装配重放、悬吊物理与稳定性检查；不通过就如实失败，不降级宣称成功。
- **真实斜坡与悬吊**：正/反斜坡按真实模具的凸点与承托关系建模；垂耳、下垂手臂等无下层直托的零件由上方跨接大砖吊挂，并提取为预拼子组件。
- **版本化产物**：每次通过检查的设计自动求解并保存为独立版本，产物带 schema 版本，读取端向后兼容。

## 双生成模式

| 模式 | 做什么 | 适用 |
|---|---|---|
| 快速（默认） | 跳过视觉评审与视觉修订，仍完成部位绑定、结构修订、精确求解与统一校验 | 想尽快拿到可拼初稿 |
| 高保真 | 增加多视角渲染 + 视觉评审 + 有界外观修订，达标后求解 | 更在意外观相似度 |

- 高保真硬失败且剩余时间足够时，会用同一原始需求自动快速保底**恰好一次**。
- 交付结果如实区分：`fast_success`、`fidelity_success`、`fidelity_degraded`、`fast_fallback`、失败/取消。
- 快速模式不显示虚构评分，也不把“未评审”当 0 分。

## 真实限制

- **生成质量有波动**：真实模型产出存在降级交付、快速保底与失败；固定主链保证“不通过校验就不算成功”，但不保证每个需求都能一次成功。
- **平台范围**：Python 服务端 + Web 端 + Android APP（Flutter）。当前没有 iOS 工程、签名与构建验收。
- **模型依赖**：需要用户自备兼容 OpenAI Chat Completions 的服务端点与模型；不同模型的效果差异明显。
- **时间预算**：单任务有 30 分钟硬墙钟，最后 90 秒停止模型调用；到点会如实报告失败类别。
- **不是 LEGO 官方产品**：本项目是独立开源项目，与 LEGO Group 无隶属、赞助或背书关系，相关商标归原权利人。
